# Claude Code × Crazyrouterで使うプロンプト最適化の実践パターン

Claude CodeをCrazyrouter経由で使う場合、最初に確認すべきなのは接続設定です。Claude CodeやAnthropicネイティブクライアントでは `ANTHROPIC_BASE_URL=https://cn.crazyrouter.com` を使います。OpenAI互換SDK、HTTPリクエスト、バックエンドやフロントエンドのアプリでは `base_url=https://cn.crazyrouter.com/v1` を使います。ここを混同すると `/v1/v1/...` のようなパスになり、原因が分かりにくいエラーになります。

設定が安定したら、次に効いてくるのはプロンプトの品質です。Claude Codeに「直して」「改善して」とだけ伝えると、モデルは目的や制約を推測します。結果として、不要なリファクタリング、過剰な変更、期待と違う出力形式が起きやすくなります。

## よいプロンプトの基本

実務では、次の要素を明示すると安定します。

- 何をしてほしいか
- 対象ファイルや対象機能
- 変更してよい範囲
- 変更してはいけないもの
- 出力形式
- 前提や業務上の背景

悪い例:

「ログイン処理を直して」

改善例:

「OAuthコールバック後にユーザーが `/login` に戻される原因を調査してください。まず `auth/callback.ts`、`middleware.ts`、セッションCookie処理を確認し、ファイル編集の前に原因候補と確認ポイントをMarkdownの箇条書きで返してください。」

このように、調査なのか実装なのか、どのファイルを見るのか、いつ編集してよいのかを分けるだけで、結果はかなり扱いやすくなります。

## 出力形式を指定する

Claude Codeには「表で」「チェックリストで」「PR説明文として」など、期待する形式を明確に伝えます。

```markdown
タスク: 認証ミドルウェアをレビューしてください。

対象:
- middleware.ts
- lib/session.ts
- app/api/auth/*

出力形式:
| 領域 | 指摘 | リスク | 修正案 |
|------|------|--------|--------|

ルール:
1. まだファイルは編集しない
2. 推測は「前提」として分ける
3. 不明点があれば最後に質問を書く
```

この形にすると、レビュー、設計、実装を分離できます。特に認証、課金、データ移行のような影響範囲が広い作業では有効です。

## 複雑な作業は段階化する

一度に「調査して、実装して、テストして、ドキュメントも書いて」と依頼すると、意図しない変更が混ざることがあります。おすすめは次の流れです。

1. 現状調査
2. 変更計画の提示
3. 人間が確認
4. 実装
5. テスト追加または確認
6. PR説明の作成

たとえば「まず請求書作成フローを調査してください。編集はしないでください。関係ファイル、現在の流れ、リスク、最小変更案を返してください」と依頼します。その後、計画を確認してから実装を依頼します。

## 制約を書く

実装依頼では制約が重要です。

- public APIを変えない
- DBスキーマを変えない
- 依存パッケージを追加しない
- 既存のテストスタイルに合わせる
- 生成ファイルは編集しない
- まず質問してから仮定する

Crazyrouter関連のドキュメントを生成させる場合は、APIエンドポイントにトラッキングパラメータを付けないことも明記します。GitHubガイドはこちらです: [claude-code-guide](https://github.com/xujfcn/claude-code-guide?utm_source=zenn&utm_medium=article&utm_campaign=claude_code_guide_daily)

プロンプト最適化は魔法の言葉探しではありません。よい作業指示を書くことです。Claude Codeを「文脈を共有すれば強い開発者」として扱い、目的、制約、形式、確認手順を渡すと、日常の開発ワークフローに組み込みやすくなります。
